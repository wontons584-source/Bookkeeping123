## 一、增量背景与范围

### 1.1 为什么要有 v2

本产品是「工程项目认知实践课程」作业，课程要求从 0 到 1 用 AI 技术实现一个**具备 AI 能力的应用系统**，其中任务 3 明确要求：**「运行所开发的系统，注册不同类型的账号，演示全流程」**。

v1 的"无账号、纯规则"与课程要求硬冲突：

| 课程要求 | v1 现状 | 冲突 |
|---|---|---|
| 注册不同类型的账号 | 无任何账号体系 | 硬冲突，v2 增量一解决 |
| 具备 AI 能力的应用系统 | 规则版固定建议（写死 3 条） | 弱冲突，v2 增量二升级为端侧 AI |

### 1.2 v2 增量范围（一句话）

- **增量一：多账号体系与数据隔离**——注册/登录、学生/家长两种角色、per-user 数据隔离、v1 数据自动迁移、家长邀请码绑定与只读视图。
- **增量二：端侧 AI 三件套**——语音记账（v1 已有，保留并接入推荐）、智能分类推荐（新增）、AI 消费洞察引擎（升级）。全部**本地规则引擎**实现，不接云端大模型。

### 1.3 不变约束（v1 全部沿用，逐条重申）

以下约束在 v2 中**逐条仍然生效**，任何一条被破坏即验收失败：

1. file:// 协议双击 index.html 直开可用，不允许"起个服务才能用"成为默认方式
2. 无后端、无服务器、**无任何网络请求**（v2 新增的注册/绑定/推荐/洞察全部在本机完成，零请求）
3. 数据只存本机浏览器 localStorage（账号表与 per-user 数据），登录态存 sessionStorage
4. 金额一律以"分"为整数单位存储，禁止 float（v1 验收第 7 条口径不变）
5. 经典 script 多文件，无 ES modules、无构建工具、无 npm 依赖、无 CDN 外链
6. Chart.js 沿用本地文件 lib/chart.js（v4 UMD），只用饼图，不换库
7. 测试用 Node 原生 assert 断言脚本，不引入测试框架；浏览器交互靠手动验收清单
8. OCR 仍为占位按钮（无识别代码路径）；继续不做云端 LLM API、OCR 真识别、云同步

### 1.4 v2 明确不做（增量负面清单）

| 不做 | 为什么 |
|---|---|
| ❌ 云端大模型 API / 任何联网 AI | 延续 v1"零网络请求"底线；端侧规则引擎可解释、可测试、可验收 |
| ❌ OCR 真识别 | 同 v1，占位保留 |
| ❌ 修改密码、找回密码、删除账号 | 课程演示不需要；找回密码无邮箱/手机通道，做了就是假的 |
| ❌ 注册邮箱/手机号验证 | 无后端无网络，验证不了；用户名 + 密码即完整注册 |
| ❌ 密码加密存储（可逆加密） | 哈希即够（见 5.2）， reversible 加密属过度设计且容易写成明文等价物 |
| ❌ 多设备同步、数据导出 | 同 v1 不做清单 |
| ❌ 家长端修改学生任何数据 | 只读是硬边界，见 3.2 线六 |
| ❌ 一个学生绑定多个家长 / 一个家长绑定多个学生 | 一对一即可满足课程"不同类型账号演示"；多对多徒增状态复杂度 |

## 三、业务流程与状态增量

### 3.1 主流程增量

**认证线（新增前置）**：打开页面 → 未登录则只见登录/注册页 → 登录成功 → 按角色分流：
- 学生 → 进入 v1 主流程（录入账单 → 列表 → 饼图/洞察/总资产重算），所有读写作用于该学生的 per-user 数据
- 家长 → 已绑定则进入只读视图，未绑定则进入绑定引导页

v1 的账单主流程、账户线、语音线**逻辑不变**，只是数据源从全局键换成当前登录学生的 per-user 键。

### 3.2 状态迁移表增量

v1 的 T1–T8（账单条目 / 视图联动 / 语音口述）全部沿用，编号不变；下表为**新增状态线**。凡是 v1 的"用户""存储"在本表中均指"当前登录学生"及其 per-user 存储；`users` 表结构见 6.2。

**线四：账号与会话**

| 编号 | 从哪个状态 | 什么动作 | 到哪个状态 | 谁能做 | 什么条件 | 副作用 |
|:--:|---|---|---|---|---|---|
| T10 | 未注册 | 填注册表单并提交 | 已注册（未登录） | 未登录访客 | 用户名合法且不重名、密码合法、角色已选（见 6.2） | users 表新增一条（含密码哈希）；自动以该账号登录（→T12） |
| T11 | 未登录 | 输入用户名密码点登录 | 已登录（学生或家长） | 未登录访客 | 用户名存在且密码哈希匹配 | sessionStorage 写入会话；跳转对应角色视图 |

| T17 | 未绑定 | T16 绑定成功 | 已绑定 | 已登录家长 | 同 T16 | 家长下次登录直达学生只读视图 |

**线七：v1 数据迁移**（一次性，触发时机钉死为"**首个学生账号注册成功**"，不是"每次启动检测"，也不是"登录时"）

| 编号 | 从哪个状态 | 什么动作 | 到哪个状态 | 谁能做 | 什么条件 | 副作用 |

| T21 | 旧数据待迁移 | 注册成功但迁移写入失败 | 迁移失败（旧数据保留） | 系统（自动） | per-user 写入抛异常（如配额满、JSON 异常） | **旧键原样保留**，可下次重试；该学生账号为空状态；页面弹提示，绝不崩溃 |

**线八：智能分类推荐**（纯前端即时计算，无持久化状态）

| 编号 | 从哪个状态 | 什么动作 | 到哪个状态 | 谁能做 | 什么条件 | 副作用 |
|:--:|---|---|---|---|---|---|
| T22 | 无推荐 | 在商户或备注输入框键入文本 | 有推荐卡片 | 用户 | 输入文本命中词典 ≥1 词条 | 表单下方展示"分类 + 刚性/冲动"推荐卡，附命中理由 |
| T23 | 有推荐卡片 | 点"采纳" | 推荐已填入表单 | 用户 | 无 | 表单的分类、刚性/冲动标签被替换为推荐值（用户仍可再改）；推荐卡收起 |
| T24 | 有推荐卡片 | 点"忽略"或继续修改输入文本 | 无推荐 / 换新推荐 | 用户 | 无 | 不改动表单任何字段；推荐不落库（落库仍走 T1） |

**AI 洞察不是状态线**：洞察每次视图重算时即时生成（纯函数），无持久化、无用户操作状态，验收按输出内容判定（见七）。

> 每个新状态的出边检查：未注册→T10/T11；已注册未登录→T11；已登录→T12/T14/T15/T19；无有效码→T14；有有效码→T15/T16；未绑定→T16；已绑定→T18/T19；待迁移→T20/T21；无推荐→T22；有推荐→T23/T24。无死状态。

### 3.3 异常路径增量

v1 3.3 的四类异常（语音失败、误删取消、多标签页冲突、数据损坏）全部沿用，且"数据损坏重置"逻辑**下沉到 per-user 键级别**（某学生的键损坏只重置该学生的数据，不波及他人）。以下为 v2 新增：

**⑤ 注册异常**
- 用户名重名：提示"用户名已存在"，停留注册页，已填密码保留
- 用户名/密码不合法（空、超长、含冒号等，规则见 6.2）：逐项提示，不提交
- 注册过程中存储写入失败（配额/异常）：提示注册失败，users 表不写入半条记录（先组装完整对象再一次写入）

**⑥ 登录异常**
- 用户名不存在或密码错误：**统一提示"用户名或密码错误"**，不区分哪种、不提示"该用户名未注册"（避免变相枚举账号；课程演示同样按此口径验收）
- 登录后 sessionStorage 会话指向的用户在 users 表中已不存在（手工改存储）：按未登录处理，清会话回登录页

**⑦ 邀请码异常（家长绑定侧）**
- 码不存在（无此码或已失效/已被使用）：统一提示"邀请码无效"，**不区分**"不存在/已失效/已被用过"三种情况
- 码有效但该学生已绑定其他家长：提示"该学生已绑定家长"，绑定失败，学生码不动
- 家长试图绑定自己：不可能发生——码只属于学生角色，家长名下永远没有码（若输入的是任意学生码，按正常绑定流程走）

**⑧ 未登录/越权访问**
- 未登录时访问任何受保护视图（记账/账户/只读视图）：一律重定向登录页，不渲染任何业务数据
- 家长登录后未绑定：只显示绑定引导页 + 退出登录按钮，不出现任何学生数据区
- 家长端 DOM 中不得存在账单表单、删除按钮、账户编辑等任何写入口（不是"隐藏"，是"不渲染"）

**⑨ 迁移失败**
- 见 T21：旧键保留、新账号空状态、页面弹提示可继续使用，绝不崩溃
- 旧键 JSON 损坏（非法 JSON）：按"无旧数据"处理（沿用 v1 损坏重置思路），正常注册，不迁移不报错

## 四、术语增量

| 术语 | 准确定义（要写到能判定） | 易混淆的说法 |
|---|---|---|
| **账号** | users 表中的一条记录：用户名 + 密码哈希 + 角色 + 创建时间 +（学生）邀请码 +（家长）绑定的学生用户名 | ❌ 和 v1 的"账户"（微信/支付宝那种放钱的地方）混用——**账号是登录身份，账户是钱袋**，全文严格区分 |
| **角色** | 账号注册时选定且**终身不可改**的枚举：`学生` / `家长`。学生拥有 v1 全部功能；家长仅只读 | ❌ "家长账号升级成学生"——不存在角色切换功能 |
| **邀请码** | 学生账号名下的一次性 6 位数字码。同一时刻每个学生至多一个有效码；被成功使用或被重新生成后立即失效 | ❌ "邀请码长期有效可反复使用"——一次性，见线五 |
| **绑定** | 家长账号与**一个**学生账号之间的一对一只读授权关系，关系数据**只存在家长记录的 bound_student 字段一处**（学生端绑定状态靠反查 users 得出，不做双写）。解绑 = 清空该字段 | ❌ "学生记录里也存一份 bound_parent"——禁止双写，两处各改各的必然不一致 |
| **只读** | 家长视图只能读绑定学生的当月统计数据（饼图、洞察、总资产），DOM 中不存在任何写操作入口。家长看的是**实时数据**（每次进入按学生当前 per-user 数据重算），不是快照 | ❌ "把学生数据复制一份给家长"——不复制，实时读 |
| **洞察** | 由洞察模板库 × 当月统计数据动态生成的分析文案，每次 2–4 条，每次重算即时生成、不落库。与 v1"消费分析固定 3 条建议"的关系：**v1 的建议规则整体废弃，由洞察引擎替代** | ❌ "洞察和建议并存"——v2 分析区只有洞察一种输出 |
| **推荐采纳** | 用户点推荐卡上的"采纳"，把推荐结果（分类 + 刚性/冲动）填入表单字段。采纳前**不落库**，采纳后用户仍可手改，最终以 T1 保存时的表单值为准 | ❌ "推荐直接生成账单"——推荐只动表单，落库永远经用户点保存 |
| **迁移** | v1 全局键 `bills`/`accounts` 的旧数据一次性搬到首个注册的学生账号 per-user 键下的过程。先写后删，失败保留旧键 | ❌ "每次启动都检查迁移"——只做一次，触发时机见 T20 |

```
│   └── auth.test.js       # 新增（哈希确定性、邀请码、迁移决策）

```

依赖方向仍单向：app → auth / recommend / insights / stats / store / speech；recommend、insights、auth 不依赖 app 和 store。

### 5.2 密码哈希（硬性规则）

- 存储的是哈希值，**任何情况下 users 表中不得出现明文密码**（验收 A2 专门卡）
- 首选 `crypto.subtle.digest('SHA-256', ...)`；**若 file:// 环境检测不可用，退化为内置 JS 简易哈希**
- 退化哈希必须是**确定性**的：同一密码每次计算结果必须完全一致（否则第二次登录永远失败）——这是退化实现最容易写错的地方，auth.test.js 必测
- 哈希函数旁必须加代码注释：**"课程演示用途，非生产级安全；无盐、无慢哈希，生产环境禁止照搬"**
- 密码校验：登录时把输入密码走同一哈希函数后与存储值比对

### 5.3 会话态

- sessionStorage 键 `ledger_v2:session`，值为 `{ username, role }` JSON
- sessionStorage 由 store.js 统一读写（与 localStorage 同一纪律）
- 刷新保持登录（sessionStorage 生命周期随标签页）；关闭浏览器即退出；多标签页同浏览器共享登录态（同一 sessionStorage 不跨标签页，属浏览器行为，不另行处理，沿用 v1"最后写入为准"的取舍口径）

### 5.4 端侧 AI 三件套实现约束

**① 语音记账（保留）**：speech.js 与 v1 完全一致；唯一变更是预填成功（T6）后**触发一次 recommend 匹配**（对识别出的商户/备注文本），展示推荐卡。识别失败降级路径沿用 v1 4.3。

**② 智能分类推荐（新增）**
- `recommend.js` 纯函数：`recommend(text) → { category, tag, reason, hit } | null`
- 内置中文关键词词典 **≥40 词条**，覆盖 6 大分类与商户名/口语词，示例（非全集）：
  - 餐饮：奶茶、蜜雪冰城、瑞幸、食堂、外卖、美团、饿了么、早饭、午饭、晚饭、宵夜、火锅……
  - 交通：打车、滴滴、地铁、公交、共享单车、高铁、加油……
  - 娱乐：盲盒、游戏、电影、KTV、演唱会、网吧……
  - 学习：笔、书、打印、复印、网课、考试报名费……
  - 日用：洗衣液、纸巾、洗发水、快递……
  - 其他类词条酌情配置
- 每个词条携带 `{ 分类, 刚性/冲动 }` 推荐值（如 奶茶→餐饮+冲动；食堂→餐饮+刚性；地铁→交通+刚性；盲盒→娱乐+冲动）；**推荐只动表单，永不直接生成账单**
- 理由文案必须包含命中词本身（验收 A9 判定"理由含命中词"）
- 一个文本命中多个词条时：取**第一个命中词条**（词典按数组顺序优先），不做权重排序——简单、可解释、可测试
- 无命中 → 返回 null，界面不出推荐卡

**③ AI 消费洞察引擎（升级，替代 v1 固定建议）**
- `insights.js` 纯函数：`generateInsights(bills, accounts, now) → string[]`
- 模板库 **≥10 个模板**，按五类组织，每类至少 2 个：
  - **结构类**：本月最大占比分类（"本月餐饮占 52%，是最大头"）、冲动占比结构
  - **对比类**：本月 vs 上月总支出环比增减、某分类环比增减（上月无数据则该模板不触发）
  - **习惯类**：高频小额（同分类笔数 ≥5 且多为小额）、大额单笔
  - **风险类**：冲动消费占比 ≥30% 预警
  - **资产类**：本月支出 vs 账户总资产的余额消耗（"按这个速度，当前家底还够撑 X 天"）
- 每个模板定义**触发条件**（最少样本量，如结构类需本月账单 ≥3 笔、对比类需上月有账单）；对满足条件的模板按"相关度"（占比/环比幅度等数值大小）排序，**取前 2–4 条**生成
- 数据不足（本月账单 <3 笔）：不输出洞察，输出引导话术，如"当月记账满 3 笔解锁消费洞察，再记 X 笔就好"——话术文案与解锁条件必须与模板触发条件同源（一处常量）
- 输出条数必须落在 [2, 4]（有足够数据时），上限截断、下限由引导话术兜底

### 5.5 存储访问纪律（强化）

- store.js 仍是**唯一**允许读写 localStorage 与 sessionStorage 的文件
- per-user 键名一律经**一个统一函数**拼装（如 `userKey(username, kind)`），禁止在多处手写字符串拼接——用户名合法规则中禁冒号（见 6.2）就是为了让键拼装无歧义
- v1 全局键 `bills` / `accounts` 在 v2 代码中**只允许出现在迁移逻辑里**（读旧、删旧），业务读写一律走 per-user 键

## 六、数据模型增量

### 6.1 键结构

| 键 | 内容 | 变更说明 |
|---|---|---|
| `schema_version` | 数字 `2` | 升版；读取代码按版本兼容（=1 视为"有待迁移旧数据"信号之一） |
| `ledger_v2:users` | 账号表数组 | 新增 |
| `ledger_v2:{用户名}:bills` | 该学生的账单数组 | 取代全局 `bills`；数组内字段结构与 v1 6.2 完全一致，不改字段 |
| `ledger_v2:{用户名}:accounts` | 该学生的账户数组 | 取代全局 `accounts`；字段结构不变 |
| `ledger_v2:session`（sessionStorage） | `{ username, role }` | 新增 |
| `bills` / `accounts`（v1 旧键） | v1 旧数据 | 只在迁移中被读和被删；迁移成功后不存在 |

示例形状：

```
键：ledger_v2:users
值：[
  {
    "username": "linxiao",
    "password_hash": "a1b2c3…（64 位十六进制）",
    "role": "学生",
    "created_at": 1792635059000,
    "invite_code": "382916",          // 学生：当前有效码，无有效码为 null
    "bound_student": null             // 学生恒为 null，字段仅家长使用
  },
  {
    "username": "linmama",
    "password_hash": "d4e5f6…",
    "role": "家长",
    "created_at": 1792636000000,
    "invite_code": null,              // 家长恒为 null
    "bound_student": "linxiao"        // 绑定关系唯一存放处
  }
]

键：ledger_v2:linxiao:bills      → 形状同 v1 bills
键：ledger_v2:linxiao:accounts   → 形状同 v1 accounts
```

### 6.2 关键字段约束

**users 表：**

| 字段 | 类型 | 约束 | 取值/说明 |
|---|---|---|---|
| username | string | 非空，1–20 字符，**禁止包含冒号 `:` 与前后空格**，同表唯一 | 用户名进键名拼装，冒号会撞键格式，故在注册时校验拦截 |
| password_hash | string | 非空 | 哈希十六进制串；**禁止存明文**（验收 A2） |
| role | string | 非空 | 枚举 2 值：`学生` / `家长`，注册后不可改 |
| created_at | integer | 非空 | 毫秒时间戳 |
| invite_code | string/null | 学生：6 位数字或 null；家长：恒 null | 全表同一时刻至多一个学生持有同一码值（生成时查重） |
| bound_student | string/null | 家长：已绑定为对方用户名（须确实存在于 users 且角色为学生），未绑定 null；学生：恒 null | **绑定关系唯一存放处**，禁止在学生记录上再写 bound_parent 双写 |

**注册校验规则（钉死，前端提示逐项对应）**：用户名非空、≤20 字、不含冒号、无前后空格、不重名；密码 6–20 位（字符不限）；角色必选。

### 6.3 迁移规则（钉死）

1. **触发时机**：仅"注册成功且角色=学生"这一刻检查一次。检查内容：v1 全局键 `bills` / `accounts` 是否存在且能解析出非空数据
2. **迁移动作（顺序不可换）**：① 读旧键并校验 → ② 整体写入该学生 `ledger_v2:{用户名}:bills` / `:accounts` → ③ 写入确认成功后**才**删除旧键 `bills` / `accounts`
3. **失败处理**：任一步抛异常 → 停止，**旧键原样保留**（可重试），该学生账号为空状态，页面弹提示，绝不崩溃
4. **损坏处理**：旧键 JSON 非法 → 视为无旧数据，跳过迁移，不报错（沿用 v1 损坏重置思路）
5. **一次性**：迁移成功后旧键已删，后续注册自然无旧数据；不存在"迁移标记位"，也不做"每次启动检查"
6. **归属唯一**：旧数据只迁给**第一个注册的学生账号**；若第一个注册的是家长，旧数据继续保留待迁，直到首个学生注册

## 九、协作方式与优先级

**沿用 v1 需求书第九节（协作方式）与第十节（优先级冲突时的取舍）全部条款，不重抄。** v2 补充两条：
